# Project Guidance

## Product direction

This project includes a modernized Geiss visualizer for Apple Silicon Macs, alongside the original Windows screensaver and Winamp plug-in. The macOS product is a standalone app. Keep the visualization engine independent of the app shell so it can potentially be reused by a macOS screen saver later.

Treat [`docs/spec/macos-port.md`](docs/spec/macos-port.md) as the current product brief. Update it when the user makes a design decision. When guidance here and the spec diverge, follow the latest user decision and reconcile the documents.

## Agreed product decisions

- Target Apple Silicon only.
- Start with macOS 14.2 as the minimum deployment target; raise it if required by the chosen rendering or other APIs. No fallback for older macOS versions is required.
- React to system output, including music, notifications, and other sounds. Music playback controls and player-specific integration are out of scope.
- Start as a standalone app and visualize on the main display. Keep a future screen saver path viable; multi-display behavior can be considered later.
- Use a modernized interpretation of Geiss: retain recognizable procedural maps, waveforms, rich colors, layered effects, and evolving visuals while refining rendering, motion, and visual balance.
- Visuals evolve automatically. Pause freezes the picture. Lock holds the current map, waveform, and effects while audio motion continues; colors keep following the sound. Next visual advances the look.
- The picture is truecolor, as the original's 32-bit mode; there is no palette. Sound-synced color is always on, with no control.
- On HDR screens, fixed textures (mode 6's edges, the grid, crystals) are held to SDR and never glow; lines, chasers, and other effects can.
- The first controls are sensitivity (persisted), pause, lock, and next visual. Size and the other legacy settings wait. Do not add visualizer controls without user direction.
- Layered effects draw only while there is sound. In silence, and when capture is denied or fails, they rest until sound returns, except the nuclide, which drops the original's random rings in silence.
- On launch, open the visualizer immediately. When audio permission is missing, denied, or the tap fails, keep a calm visual and show an overlay that opens System Settings. Silence with permission granted shows the calm visual and no error.
- Initial distribution is local. Before public distribution, review applicable license and attribution requirements, bundled assets, and use of the Geiss name.

## Current build

`macos/` is the SwiftUI app. `engine/` is the portable C++ picture. The root CMake project remains the Windows screensaver and Winamp plug-in. Build steps for the app are in [`macos/README.md`](macos/README.md).

The app opens straight into a window on the main display. The window starts at 1280×720, can shrink to 640×360, and uses the system fullscreen control. The bundle identifier is `com.janrothen.geiss`. Local builds are ad-hoc signed and are not sandboxed. The minimum system is macOS 14.2 on Apple Silicon.

The picture keeps the same warp and has all 25 of the original's map modes (`engine/src/map.cpp`) and all 6 waveforms. Looks are picked with the original's weights and excluded pairs; the spec's Prototype milestone section lists each formula and every intentional difference. Each look also picks the original's layered effects (`engine/src/effects.cpp`): chasers, bar, dots, solar, grid, nuclide, and shade bobs, with its per-map weights, plus each map's center darkening. The original's unused spectral dots (three discs driven by bass, middle, and treble levels from the analyzer) and its commented-out crystals are ported too, each with this port's weight of 100 on every map, and mode 6 draws the commented-out edges. The commented-out neutrons are left out. The nuclide and spectral dots can replace the waveform, and mode 5's map follows the nuclide. Effects rest in silence, except the nuclide's random rings, about one reference frame in 12. After 1.5 s of silence, or of sound whose line would draw dimmer, by its brightest channel, than the idle wave's drift color at a brightness of 26 on RenderWave's 0…155 scale (the drift's average over time, about 41), an idle wave rises over 4 s: a made-up slow signal drawn with the look's own waveform, in the color drift at a low brightness, breathing in size and brightness, so silence and a denied tap keep a calm moving picture instead of black (`engine/src/engine.cpp`). Louder sound fades it out over 0.5 s, and quiet during that fade brings it back without the wait. The window opens on mode 25 and waveform 1. Next, and the 20-second timer, pick a different pair and new effects. Lock holds the pair and its effects. Pause freezes the picture and that timer. The simulation is truecolor, as the original's 32-bit mode: red, green, and blue per pixel in four bytes, warped alike. The waveform takes the original's sync-to-sound color from a 24-band spectrum the analyzer measures (a direct Fourier sum over the original's 5.8 ms of left samples, 256 at 44.1 kHz): bass red, middle green, treble blue, with 3% of a slow color drift (`engine/src/color.cpp`). The effects use the original's truecolor forms: tinted nuclide rings, a color-fringed bar, color-cycling dots, per-channel shade bobs, solar particles, and edges, and colored spectral dots. The engine expands the buffer to RGBA8 with the original's doubled display (`min(255, 2c)`), and Metal uploads that buffer, or, on the GPU path, a kernel expands it. On Apple Silicon the warp and the expansion run as Metal kernels over the engine's own frame memory, shared without a copy (`macos/Geiss/Shaders.metal`, `GeissGPU` in the bridge); the effects, waveform, and maps still draw on the CPU, and the engine includes no Metal. Each frame's warp is committed right after the frame before it is presented, with that frame's sound for the effects, so the GPU warps between frames and the next tick only waits for a finished warp (`Engine::startNextWarp`). The simulation has one pixel per window point, so fullscreen on a 5K screen is 2560×1440; the CPU path, kept as the reference (`-GeissCPUWarp YES`), caps the longest side at 960. `-GeissWarpCheck YES` prints how far the GPU warp is from the CPU's. The shaders compile at launch from the bundled source, so building needs no Metal toolchain. Each frame warps the previous frame through the map and darkens it, rounding each pixel up or down at random so the darkening survives high frame rates. A display link ticks the picture once per screen refresh, up to 120 Hz on ProMotion, with time measured between its target times; while paused it asks for about 15 Hz and redraws without an upload. The map build, and the CPU warp, run in 16 row bands that the bridge spreads over the cores with Grand Central Dispatch; the engine starts no threads itself. A new window size applies once it has held for 0.15 s, except during the window's first 0.15 s, when sizes apply at once. Paused redraws hold an in-flight slot like uploads, so the texture rotation never rewrites a texture the GPU is reading. The texture is sRGB, so the texture unit decodes the colors. On an HDR screen the hottest pixels glow up to 2.5 times SDR white, or the screen's headroom if lower; the engine passes each pixel's highlight level in alpha for that, rising from 0 to 255 as its brightest stored channel goes from 128 to 208. Fixed textures (mode 6's edges, the grid, crystals) are held to SDR: each pixel's fourth byte holds how much of its brightness they set, warps with the colors, and keeps that share out of the highlight. Only a screen whose potential headroom reaches 2.5 counts as HDR and asks for EDR; SDR screens with a little backlight headroom draw without highlights. The drawable is tagged with a linear copy of the screen's own color space, to keep the colors of the earlier unmanaged output.

The app taps the default output mix. Playback continues. The audio callback only copies the 32-bit float tap stream into a preallocated ring. It never waits on a lock; it drops a block if the reader is copying. A tap with no callbacks for three seconds is restarted. The C++ analyzer turns those samples into one frame, and the engine reads that frame on the main thread. The waveform spans the newest columns / 88200 s of sound, as the original did, starting at a rising zero crossing. The tap is recreated when the default output device changes, stopped on sleep, and started again on wake. Visual > Tone (⌘1) and Visual > Silence (⌘2) override the live mix while the tap keeps running, and Visual > System Audio (⌘0) returns to it. A failed tap keeps a calm picture and shows an overlay that opens System Settings. A denied tap has no error code: macOS creates it and delivers exact zeros, and asks only once. So when another app runs audio output and the tap has heard only exact zeros for 2 seconds, checked every half second, the overlay says Geiss may not hear this Mac and points to System Audio Recording Only. Permission applies when a tap is created, so returning to the app rebuilds a silenced tap, at most every 5 seconds. The first non-zero sample clears the overlay, and so does no other app running output. The spec's When audio permission is missing section has the observed behavior.

The window controls are sensitivity (persisted, default 1.0), pause, lock, and next visual. The bar hides after a few seconds. Space pauses, L locks, and N or the right arrow advances the look. I toggles a debug readout in the top-left corner with the FPS, the map, the waveform, the effects, and the HDR gain, named as in [`docs/glossary.md`](docs/glossary.md). It starts hidden and is not persisted.

Beats come from a bass-focused port of the original detector (`engine/src/beat.cpp`). In beat mode the waveform flashes on hits and goes dark between them, except the oscilloscope, and a due look waits up to 5 seconds for a big beat. A third of the looks also drift on beats with the original's slide shift (`engine/src/shift.cpp`), which holds until the next peak or a look without it. Lock and Next are unchanged. The spec's Beat response section has the details.

Still ahead: chunked map generation, size and quality settings, presets, multi-display, a screen saver host, sandboxing, and public distribution wait.

## Porting guidance

- Preserve the existing visualization algorithms and their intent where practical, in new portable C++. The simulation buffer is truecolor, red, green, and blue per pixel; the warp and the expansion to RGBA8 run on the GPU over the engine's shared memory, with the CPU versions kept as the reference. The current formulas are all 25 map modes, all 6 waveforms, and 9 layered effects. Each frame feeds the previous frame back through the map. A new pair is chosen about every 20 seconds unless locked. Treat the DirectDraw and software-pixel path, including the x86 assembly warp, as an implementation detail to replace. Keep that engine independent of the app shell for possible future screen saver reuse. The legacy Windows sources stay out of the macOS build.
- SwiftUI owns the window and controls. A small Objective-C++ bridge is the only file that includes both Cocoa and the engine.
- Replace Windows-specific platform, audio, and UI layers with suitable macOS components.
- Do not carry over Winamp integration, CD playback/control, Windows mixer/device selection, DirectDraw display-mode controls, or other Windows-only compatibility behavior into the macOS product.
- Avoid treating old frame counts, color-depth assumptions, or hardware workarounds as product requirements. Use frame-rate-independent timing and modern display capabilities where appropriate.
- Keep system-audio capture and visualization processing decoupled from the app UI. Make permission state and capture failures understandable to the user.
- Preserve existing source and assets unless the user asks to remove them or the port plan explicitly makes them obsolete.

## Working approach

- During brainstorming and specification work, do not implement application code unless the user explicitly asks to begin implementation.
- Keep changes focused on the requested task.
- Always add tests for new code in the same change. Engine code gets assertions in `engine/tests/`. App, bridge, and capture code without an automated test harness gets a manual check in the PR description instead, until such a harness exists.
- Before every commit, build and run the engine tests (see [`macos/README.md`](macos/README.md)) and commit only when they pass.
- After changing the app, build it and launch it so the user can test it by hand.
- Keep `engine/`, the Objective-C++ bridge, and `macos/` clean under the pre-commit hooks (`pre-commit run --all-files`): clang-tidy per [`.clang-tidy`](.clang-tidy) and SwiftLint per [`.swiftlint.yml`](.swiftlint.yml). Fix findings rather than adding `NOLINT`, unless the check is wrong for that line, and say why in the comment. The legacy Windows sources are not linted.
- Explain important design assumptions and unresolved product questions in the spec rather than silently deciding them.
